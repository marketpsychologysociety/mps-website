# Telegram webhook journal tests

Run the synthetic contract and mocked Apps Script adapter tests with Node.js:

```sh
node --test tests/telegram-webhook/*.test.mjs
```

## Files

- `durable-update-journal.mjs` — injected-store state machine for update deduplication, retry, reconciliation, claim fencing, and manual review.
- `durable-update-journal.test.mjs` — contract tests using SharedMemoryJournalStore. The shared in-memory Map simulates adapter recreation only; it is not durable production storage.
- `gas-spreadsheet-journal-adapter.gs` — isolated Google Apps Script spreadsheet adapter candidate. It is not connected to doPost/processTelegramUpdate_ and does not create a sheet, read Script Properties, or select a spreadsheet implicitly.
- `gas-spreadsheet-journal-adapter.test.mjs` — Node VM tests with mocked SpreadsheetApp, LockService, and Utilities. These do not run inside Google's Apps Script runtime.

## Important boundaries

- The adapter requires an explicit isolated spreadsheet ID, exact pre-provisioned tab schema, and a single writer Apps Script project.
- LockService serializes cooperating executions in the same Apps Script project; Google Sheets is not a transactional database.
- The adapter must not be enabled against production data or wired into the production webhook without separate approval.
- No exactly-once guarantee is claimed. Ambiguous Telegram side effects require reconciliation or REVIEW.
- Passing these tests is not proof of deployed Apps Script quotas, persistence, concurrency, Telegram API behavior, or real-device behavior.

- `fixtures/candidate-handler-callsite-snapshot.gs` — read-only text-normalized candidate Code.gs snapshot derived from Library source SHA-256 `c9e84512fc2ac641f59f63b9b8b7fa10d113f0256f662c25ca70555a09aea8ba`, with its own fixture SHA-256 `70a2fb84ecef7e01eb86dcd95f1481ca3857e7953c6fbae2362b3314dcb64441`; text extraction may normalize bytes/newlines, so it is not claimed byte-identical; test fixture only, never deploy from this path.
- `candidate-handler-callsite-characterization.test.mjs` — extracts and executes the actual `processTelegramUpdateCore_`, `processVipJoinRequest_`, `updateVipJoinStatus_`, and `recordMpsAudit_` function bodies from the pinned candidate snapshot in a Node VM with mocked dependencies. Seven tests characterize the four missing metadata call paths, status-before-effects ordering under one ScriptLock, and swallowed audit persistence errors. Passing reproduces known gaps; it does not mean the gaps are acceptable or fixed.
- `candidate-link-replay-reconciliation.test.mjs` — extracts and executes the current candidate application and legacy Telegram link handlers with mocked sheet/lock services. It verifies same-identity replay after expiry, rejects different identities, and rejects mismatched persisted access/Application Ref bindings. It does not prove deployed Apps Script runtime behavior.
- `candidate-edited-message-command.test.mjs` — executes the current candidate Telegram core handler with mocked dependencies. It verifies that `edited_message` updates cannot retrigger private `/start` welcome DMs or register an unconfirmed VIP group candidate, while a new `message` `/start` still works. It does not prove deployed Apps Script runtime behavior.
- The candidate handler fixture is a snapshot, not the live Library file. Refresh and re-audit its provenance whenever candidate Code.gs changes.

- Audit retention safeguard: `recordMpsAudit_()` may prune older rows with an empty Effect Key, but it never deletes keyed effect-ledger rows. If keyed rows alone exceed the historical 2,000-row soft cap, the sheet is allowed to grow rather than sacrifice deduplication history.
- `candidates/Code.gs` — full isolated MPS v4.8 candidate based on the pinned Library Code.gs source, with the chat_member-only VIP status integration wired into `processTelegramUpdateCore_`. All `chat_join_request` / `getChatMember` reconciliation paths, including the already-joined check in `sendVipInvite_()`, are prevented from writing membership status. The candidate removes the legacy non-idempotent `recordMpsVipTickerEvent_()` writer so VIP ticker rows can only be emitted by the keyed effect ledger. It includes an explicit super-admin-only `apiAdminMigrateMemberSheetToV480(session)` operation that appends columns 19–30 only when the exact legacy 18-column header is present, verifies the resulting 30-column header, and leaves all existing member rows untouched. It is never called automatically. `apiAdminPrepareTelegramVipTransitionStorage(session)` runs only after that migration and explicitly provisions the effect-key columns and transition tabs; it too is never called by the webhook. Neither admin operation has been run against production. Provisioning appends `Effect Key` columns to the existing audit/ticker sheets and creates the two new intent/cursor tabs only when the admin explicitly invokes it. This candidate has not been deployed or tested against a live Apps Script project or spreadsheet.
- `gas-vip-transition-store.gs` / `gas-vip-transition-store.test.mjs` — scoped Google Apps Script sheet repository for durable VIP transition intents and per-member cursors. The intent schema persists member name, Telegram user ID, ticker policy, source event date, payload hash, transition/effect keys and state; the cursor stores ingress epoch, original source date and decimal update ID. Ordering is original Telegram event date first, ingress epoch second, and decimal `update_id` third. It requires the active `runExclusive(tx => ...)` capability from the effect ledger, uses explicitly provisioned tabs only, enforces cursor monotonicity, and never acquires a second lock or creates sheets. The V8 tests use mocked `SpreadsheetApp`/`LockService`.
- `gas-vip-transition-orchestrator.gs` / `gas-vip-transition-orchestrator.test.mjs` — synchronous orchestration candidate using the actual isolated effect-ledger adapter and durable transition sheet store. An optional identity/eligibility resolver executes inside the same `runExclusive` scope; one lock spans pending recovery, durable intent, two status-sheet writes, cursor, keyed ticker/audit effects and completion. `ACTIVE`, `LEFT`, and `DENIED` are journaled; only explicitly allowed `ACTIVE` transitions emit a public ticker event. Crash injection covers every persistence boundary and VM/runtime replay; these are mocked Apps Script services, not live GAS.
- `gas-vip-chat-member-handler.gs` / `gas-vip-chat-member-handler.test.mjs` — ingress adapter that preserves `update_id`, original `chat_member.date`, Telegram user ID, and payload hash. It accepts only `chat_member`, rejects missing event time/ID, filters to the configured VIP group, invokes identity resolution under the orchestrator lock, and runs optional external follow-up only after lock release. `chat_join_request` / `getChatMember` observations are not status events. The orchestrator checks the per-member cursor before retrying post-lock Telegram follow-up, so stale duplicate events cannot repeat kick/revoke actions. Unauthorized kick retries first re-check current membership and never unban an already-kicked/left user; already-invalid invite links count as revoked. No Telegram network calls occur under the lock, and no exactly-once external Telegram delivery claim is made.
- `vip-transition-recovery.mjs` / `vip-transition-recovery.test.mjs` — synthetic crash/restart contract for durable per-member activation and leave transitions, including separate member/access status writes, cursor persistence, keyed effects, and recovery before a newer opposite transition. In-memory only; not a Sheets adapter or live GAS test.

- `vip-activation-orchestration.mjs` now models a per-member event cursor persisted with member state. It orders state-changing membership events by a durable ingress epoch and canonical decimal `update_id`; source dates remain type-tagged evidence and are not compared across update types. Stale leave/rejoin updates are rejected before they can overwrite newer state. This is an in-memory contract model, not durable Apps Script storage.

- `update-epoch.mjs` / `update-epoch.test.mjs` — pure contract for assigning a local update epoch after a seven-day ingress-idle window. The caller must persist the assigned epoch with the journal row under the journal lock; replays reuse the stored epoch. This is not yet wired into the Apps Script adapter.
