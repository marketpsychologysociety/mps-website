# MPS v4.8.1 Clean Rebuild — Isolated Runbook

## Scope and safety

This rebuild source is stored under `rebuild/v4.8.1/` on the repository's `main` branch.
It is not deployed and is not connected to a production spreadsheet, Drive folder, bot, or webhook.

Use only a brand-new standalone Apps Script project and synthetic spreadsheet/folder.
Do not paste this source into the old MPS project. Do not set a production spreadsheet ID.
Do not deploy, create triggers, or register a Telegram webhook during source acceptance.

## Files

- `Code.gs`: backend source.
- `Index.html`: responsive frontend source.
- `assets/qris-regular.png`: QRIS statis merchant Toko serba ada (NMID `ID1026540347758`), supplied and explicitly approved by the MPS owner for the Regular Member fee. The frontend displays it only after a visitor registers as Regular Member; the Active IB path does not show the MPS QRIS panel.

## Required Script Properties for isolated tests

- `MPS_REBUILD_OWNER_EMAIL`: exact Google account email of the project owner. Provisioning and TOTP initialization verify `Session.getEffectiveUser().getEmail()` against this value and reject calls where the effective account is unavailable or does not match.
- `MPS_REBUILD_TEST_LABEL`: exact string `MPS-ISOLATED-TEST`. Database APIs fail closed unless this marker is present.
- `MPS_SPREADSHEET_ID`: ID of a synthetic test spreadsheet named with the prefix `MPS TEST - ` (for example, `MPS TEST - Database Member`). The spreadsheet file itself and every parent folder must have Drive sharing access set to **Restricted/Private**; publicly or domain-shared files/folders are rejected. Production-named storage is rejected.
- `MPS_PROOF_FOLDER_ID`: ID of a private synthetic Drive folder named with the prefix `MPS TEST - ` (for example, `MPS TEST - Bukti Deposit`). Its entire parent-folder chain must also be private.
- `MPS_REBUILD_ALLOW_PROVISION`: exact string `true`, only while provisioning the synthetic spreadsheet. The provisioner deletes this flag after a successful run.
- `MPS_REBUILD_ADMIN_SETUP_PASSWORD` and `MPS_REBUILD_SUPER_ADMIN_SETUP_PASSWORD`: temporary plaintext setup properties used once by `initializeMpsAdminCredentials_()`. The helper generates and stores separate salted hashes/salts, then deletes these temporary properties.
- `MPS_REBUILD_ADMIN_PASSWORD_SALT` and `MPS_REBUILD_ADMIN_PASSWORD_HASH`, plus the corresponding `MPS_REBUILD_SUPER_ADMIN_PASSWORD_SALT` and `MPS_REBUILD_SUPER_ADMIN_PASSWORD_HASH`: generated by the one-time credential bootstrap; never calculate or paste them manually.
- `MPS_REBUILD_ADMIN_TOTP_SECRET` and `MPS_REBUILD_SUPER_ADMIN_TOTP_SECRET`: created once by the isolated TOTP initializer.
- `MPS_TELEGRAM_BOT_USERNAME`: bot username without `@`, used to build the post-deposit verification link.
- Optional Telegram integration: use a **dedicated TEST bot only**. `MPS_TELEGRAM_BOT_USERNAME` must contain the word `TEST` (case-insensitive), and the bot token must belong to that exact bot; the rebuild blocks outbound Bot API calls if the TEST marker or TEST username is missing. `MPS_VIP_GROUP_ID` must point to a separate test group/channel whose Telegram title contains `TEST`; invite creation, revocation, and join-request approval/decline verify the group title before mutation. Never paste the production `MPS_Notificationnew_bot` token or use the real VIP group. Configure `MPS_TELEGRAM_CHAT_ID` only as a private test-admin backup destination, plus `MPS_TELEGRAM_WEBHOOK_SECRET` (unguessable webhook path secret).
- Optional: `MPS_MARKET_PULSE_JSON` for synthetic Pulse payload.
- Backup destination for full acceptance: `MPS_BACKUP_FOLDER_ID`, a separate private synthetic Drive folder named with the prefix `MPS TEST - ` (for example, `MPS TEST - Backup`). It must differ from the proof folder and its full parent chain must be private. The read-only validator checks it; it never creates the folder.

Never paste plaintext passwords, PINs, bot tokens, or webhook secrets into source files or chat.

Owner-only setup, webhook, trigger, validation, and backup functions end with an underscore. They are intentionally not callable through the public Web App (`google.script.run`); run them only from the Apps Script editor while signed in as the project owner. Every owner/editor operation also requires `MPS_REBUILD_TEST_LABEL=MPS-ISOLATED-TEST`; it will fail closed if that TEST marker is missing.

## Provisioning

1. Create a new standalone Apps Script project.
2. Add `Code.gs` and `Index.html` from this folder.
3. Set `MPS_REBUILD_OWNER_EMAIL` to the Google account that owns the isolated Apps Script project.
4. Create a new empty synthetic spreadsheet named `MPS TEST - Database Member`.
5. Create a new private synthetic proof folder named `MPS TEST - Bukti Deposit` and a separate private synthetic backup folder named `MPS TEST - Backup`. Ensure every parent folder is private too.
6. Set `MPS_REBUILD_TEST_LABEL=MPS-ISOLATED-TEST` and set the spreadsheet, proof-folder, and backup-folder IDs to those synthetic resources. Never use the production spreadsheet or the original `MPS - Bukti Konfirmasi` folder.
7. Set `MPS_REBUILD_ALLOW_PROVISION=true` only for the provisioning run.
8. Run `provisionMpsRebuildStorage_()` manually once from the owner account. On success, the provisioner removes the one-time allow-provision flag.
9. Run `runMpsRebuildValidation_()` from the Apps Script editor. This private editor-only entry point verifies the owner account and checks the TEST marker, resource names, exact schemas, private folder ancestry, and credentials. Inspect every returned boolean and `errors`; it does not provision or modify storage.

Provisioning creates the legacy 18-column sheet only if absent and creates auxiliary sheets only when absent. It accepts either the exact 18-column legacy header or the exact recognized 30-column v4.8 header (18 core + 12 technical columns). It rejects any other header layout. It does not clear, delete, or rewrite existing member rows or technical-column values; new member rows write only the 18 core values.

## Important implementation gaps — NOT ACCEPTED FOR PRODUCTION

This is an initial clean architecture baseline, not a production-ready release.

- Admin-only initial PIN issue/reset is now implemented: it generates a six-digit PIN, stores only salted SHA-256 hash + salt in Script Properties, and displays the PIN once in the authenticated admin UI. Admin must verify member identity and deliver it privately. Automated verified-Telegram delivery and member self-service recovery are not implemented.
- Telegram linking now issues a 32-hex-character, 24-hour single-use deep link after deposit; only the SHA-256 token hash is stored. `/start` validates that the Telegram username exactly matches the registration username before storing Telegram user/chat IDs. Webhook updates are journaled with payload JSON and completed updates are deduplicated. Because Apps Script ContentService cannot reliably return a non-2xx webhook status, processing failures are recorded as `FAILED` and can be retried from the Admin control panel. The webhook is not registered automatically.
- After a deposit, the configured private admin chat receives a backup summary of registration and deposit data. No admin Telegram message is sent at initial registration. Configure and verify the admin chat ID carefully because this message contains personal and account-related information.
- Approval is blocked until Telegram username verification is complete. If bot username is not configured, no link is issued and approval cannot proceed until the configuration is corrected.
- Admin can reissue a missing/expired Telegram link without asking the member to resubmit proof, using `apiAdminReissueTelegramLink`.
- Admin can retry failed/stale Telegram webhook updates from the control panel; the journal stores sanitized payload JSON for retry and must remain private. One-time `/start` tokens are redacted before storage; if that specific webhook fails, the update is marked non-retryable and Admin must issue a fresh Telegram link.
- Telegram update journal retains the inbound update JSON to support controlled Admin retries; restrict spreadsheet access because these payloads contain Telegram account metadata. Reissue expires older pending links.
- After approval, a VIP invitation task is queued. The Admin UI attempts to process it immediately: the bot creates a 48-hour invite link that requires a join request and sends it to the linked member. The webhook approves only the exact linked Telegram user ID; forwarded links are rejected for other accounts. Queue claims are protected against concurrent Admin clicks and stale processing can be retried. Failed deliveries remain in `RETRY`; Admin can run the VIP queue action again. If a member has not joined and a `SENT` invite is older than 48 hours, the next Admin queue run checks for an existing verified join, then creates a fresh invite and best-effort revokes the old link. Failed sends revoke the newly generated link best-effort and remain retryable.
- Bot must be an administrator of the VIP group with permission to create invite links. Configure `MPS_VIP_GROUP_ID` and Telegram webhook updates to include `chat_member` and `chat_join_request`. Confirmed `chat_member` joins are matched to an approved member by Telegram user ID; only then is the nickname published to the public VIP ticker. A verified leave removes the prior join from public display.
- VIP invitation creation, owner-bound join-request approval, confirmed join/leave events, retryable invitation queue, and public nickname ticker are implemented in source. They still require isolated Bot API/group acceptance tests.
- Admin health summary and the latest 50 audit events are available from the Admin panel. The summary omits secrets and member proof data.
- `createMpsBackupSnapshot_()` is an owner-only manual backup. It requires a separate private `MPS_BACKUP_FOLDER_ID`, refuses the proof folder, creates a timestamped spreadsheet copy, and never auto-deletes older backups.
- `installMpsWeeklyBackupTrigger_()` is an owner-run opt-in that installs one Sunday ~03:00 project-timezone backup trigger. The scheduled handler checks the effective Google account against `MPS_REBUILD_OWNER_EMAIL`, rechecks the private backup folder, and creates a private copy. It does not delete old backups. Trigger installation and a real scheduled execution/restore drill remain untested in Apps Script.
- Basic temporary per-identifier throttles now cover registration, deposit submission, and login attempts. They use Apps Script cache and are not atomic/distributed controls; robust lockout, IP/edge protection, stronger super-admin privilege separation, CSRF protections, and comprehensive authorization tests remain unimplemented.
- Admin Learning/News publishing and scheduled Public/Member announcements are implemented in source. Actual premium materials and editorial news must still be supplied by Admin; no content has been fabricated. Member billing/QRIS lifecycle and Exness IB status/rebate integration are not implemented. Binance PAXGUSDT M5 fetch logic is implemented but has not been validated against the live API from Apps Script.
- Proof uploads now stop unless the parent proof folder reports PRIVATE sharing access; each created proof file is also set PRIVATE. The owner must still verify the folder's individual editor list and test direct-file access in the isolated Drive environment.
- No physical Android/PWA acceptance, Apps Script quota test, ScriptLock contention test, live Telegram webhook test, live Bot API delivery test, actual VIP-group join/leave test, real announcement/content publishing test, or live Binance feed test has been performed.
- No deployment or production migration is authorized by this runbook.

## Admin password bootstrap (isolated project only)

1. Choose two different strong passwords of at least 16 characters and store them in a password manager.
2. In Script Properties of the isolated TEST project only, temporarily set `MPS_REBUILD_ADMIN_SETUP_PASSWORD` and `MPS_REBUILD_SUPER_ADMIN_SETUP_PASSWORD` to those two passwords. Never paste them into source code, GitHub, or chat.
3. From the Apps Script editor, run the private function `initializeMpsAdminCredentials_()` once as the configured project owner.
4. The function creates separate random salts and salted SHA-256 hashes, never returns or logs either password/hash, and deletes both temporary plaintext setup properties after successful initialization.
5. If initialization reports that temporary properties remain, delete those two setup properties manually before continuing. Do not overwrite existing credential hashes/salts; password rotation requires a separate reviewed procedure.

## Google Authenticator setup (isolated project only)

1. First configure both Admin and Super Admin password hash/salt properties.
2. In the Apps Script editor, run `initializeMpsTotpSecrets_()` once as the project owner. Setup functions compare `Session.getEffectiveUser().getEmail()` with `MPS_REBUILD_OWNER_EMAIL` and reject calls where the effective account is unavailable or does not match.
3. Add each returned `otpauth://` account to Google Authenticator on the corresponding device. The function refuses to overwrite existing secrets.
4. Keep an offline recovery copy of the secrets in an approved secure vault. Do not paste secrets or authenticator codes into chat or source files.
5. Admin and Super Admin login APIs now require password plus the current six-digit TOTP code. The HTML login screen provides separate Admin and Super Admin forms; both use separate passwords and authenticator secrets. Super Admin currently has the same review permissions as Admin; privileged Super Admin-only management actions remain to be defined.

## Telegram setup checklist (manual, isolated bot/group only)

1. Configure the bot token, bot username, private admin chat ID, webhook secret, and synthetic VIP group ID as Script Properties.
2. Add the bot to the synthetic VIP group as an administrator with invite-link permissions.
3. Deploy only the isolated TEST project after review. From its Apps Script editor, run the private owner-only `installMpsTelegramWebhook_()` helper once. It verifies the configured token belongs to the TEST bot, registers the deployed `/exec/<MPS_TELEGRAM_WEBHOOK_SECRET>` URL, subscribes to `message`, `chat_member`, and `chat_join_request` updates, and verifies the resulting webhook with Telegram `getWebhookInfo`. It does not return the webhook URL or secrets. Do not run this helper against production credentials or the production project.

5. Never use the production MPS bot/group for these acceptance tests.

## One-shot isolated acceptance suite

After configuring the isolated TEST project and its separate private backup folder, run the private editor-only function `runMpsFullAcceptanceSuite_()` once. It performs, in order:

1. Read-only configuration/schema validation (including all auxiliary sheet headers and backup-folder readability).
2. SHA-256, RFC 6238 TOTP, and Base32 deterministic crypto self-tests.
3. A temporary Admin session storage/validation round-trip; the synthetic session row is revoked in cleanup and no member row is changed.
4. One timestamped private spreadsheet snapshot in `MPS_BACKUP_FOLDER_ID`; older backups are not deleted.

The function returns a structured report and stops before later stages if an earlier stage fails. It does not install a Telegram webhook, create a weekly trigger, deploy the app, or run live Telegram/Binance/browser workflows. A successful backup stage verifies copy creation, not a restore drill.

## Deterministic crypto self-test

Run `runMpsCryptoSelfTests_()` manually in the isolated Apps Script editor. It checks SHA-256 against a known vector and six RFC 6238 HMAC-SHA1 TOTP vectors, plus Base32 decoding. This test is included in source but has not been executed in the Apps Script runtime by this audit.

## Current hardening added in source

- Regular QRIS payment proof is exposed only to Admin through a private Drive file ID link; the Admin review flow checks exact Rp100,000, payment status, private file ownership/folder, and Telegram linkage before approval.
- Membership ledger entitlement is enforced at member login, member content, and member announcement access. Regular plans expire after 30 days; Active IB plans require the corresponding membership plan to remain manually verified.
- Approval and session reads use explicit one-row, multi-column ranges.

- Admin-managed scheduled announcements support Public/Member audiences, active windows, and per-session dismissal.
- Admin-managed Learning and News records are published only through authenticated member content APIs. News source name/URL and publication time are stored; editors must provide verified sources and original summaries.
- Member Market Pulse fetches Binance Spot PAXGUSDT M5 candles when no manual JSON override exists; label explicitly states this is a gold-market proxy, not a broker Forex XAUUSD feed. Results are cached for 60 seconds.

- Public registration: temporary limit of 3 attempts per Telegram username per hour.
- Deposit submission: temporary limit of 3 attempts per Application Ref per hour.
- Member login: temporary limit of 8 attempts per Member ID per 15 minutes.
- Approved member PIN: Admin can issue/reset a six-digit PIN from the admin queue. Reset immediately invalidates the previous PIN. The PIN is returned once to the authenticated admin and is not written to Sheets or logs.
- Setup-only functions `provisionMpsRebuildStorage_()` and `initializeMpsTotpSecrets_()` verify `MPS_REBUILD_OWNER_EMAIL` against the active Google account; anonymous browser calls are rejected.
- Admin/Super Admin MFA: separate Google Authenticator TOTP secrets; API login requires password plus six-digit code with ±1 time-step tolerance. Each TOTP time step is accepted only once per role to block simple replay.
- Admin login: temporary limit of 8 attempts per 15 minutes; Super Admin: 5 attempts per 15 minutes.
- Cache keys contain a SHA-256 digest rather than raw usernames or member IDs.
- Duplicate deposit submission for the same Application Ref is rejected before another proof file is created.
- Registration validates Telegram username format and allowed membership goals. Deposit dates must be valid ISO dates and not future-dated. Uploaded proof bytes must match the claimed JPEG/PNG/WEBP signature.

These are baseline abuse controls only. They have not been load-tested or verified in the Apps Script runtime.
