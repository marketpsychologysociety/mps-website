# MPS v4.8 — Official Draw API & Data Contract

**Status:** Technical contract proposal — isolated workbench documentation only  
**Date:** 2026-11-11  
**Prerequisites:** Individual Identity & Evidence Architecture; Winner Draw Security Review; Dual Control & Audit Journal Design.  
**Safety boundary:** Contract only. No endpoint, database, sheet, identity provider, cloud resource, secret, deployment, production system, or member data was created or changed.

## 1. Purpose and implementation boundary

This document defines the proposed API surface, request/response envelopes, authorization rules, state transitions, data schemas, idempotency behavior, and public projection for a future MPS official draw subsystem.

It is **not** an implementation and does not authorize provisioning. Names below are logical endpoint names and may be adapted to the selected hosting platform after provider, ownership, cost, and retention decisions are approved.

### System separation

- Existing Apps Script Admin/CMS remains responsible for ordinary MPS announcements and content.
- A future Draw API is a separate privileged service with its own individually authenticated operators, authorization policy, state machine, and evidence journal.
- The static GitHub Pages site is a public read-only consumer of an allowlisted result projection.
- The Apps Script CMS may link to a verified public result, but it must not be able to manufacture, alter, or publish an official winner independently of the Draw API's verified state.
- The browser is never authoritative for actor identity, role, roster, eligibility, randomness, winner selection, approvals, or publication status.

## 2. API conventions

### 2.1 Transport and versioning

- HTTPS only.
- JSON UTF-8 request/response bodies.
- Versioned base path: `/api/v1`.
- Explicit schema version in durable records: `schema_version`.
- UTC RFC 3339 timestamps, e.g. `2026-11-11T12:30:00Z`.
- IDs are opaque, server-generated identifiers. Do not encode member IDs or personal data into IDs.
- Maximum request size and field lengths must be enforced by the server, not only browser validation.
- Reject unknown privileged fields rather than silently accepting them.
- Never return stack traces, provider tokens, secrets, raw roster data, or internal storage paths.

### 2.2 Standard response envelope

Successful response:

```json
{
  "ok": true,
  "request_id": "req_synthetic_01",
  "data": {},
  "operation": {
    "operation_id": "op_synthetic_01",
    "state": "COMPLETED",
    "replayed": false
  }
}
```

Error response:

```json
{
  "ok": false,
  "request_id": "req_synthetic_02",
  "error": {
    "code": "PRECONDITION_FAILED",
    "message": "The draw state changed. Refresh the event before retrying.",
    "retryable": false
  }
}
```

Messages shown to users must be generic and must not reveal whether a specific member, email, account, or private record exists.

### 2.3 Required headers

| Header | Requirement | Purpose |
|---|---|---|
| Authorization | Required on privileged API routes | Short-lived server-validated session/token |
| X-Request-ID | Required or generated by server | Trace a request without exposing secrets |
| Idempotency-Key | Required for every state-changing command | Deduplicate retries |
| If-Match / expected_version | Required for state transitions | Reject stale browser state |
| Content-Type | application/json | Request format |
| Origin / CSRF token | Required where cookie sessions are used | Prevent cross-site request forgery |

The Idempotency-Key is an operation-deduplication value, not a source of draw entropy. It must be bound server-side to actor subject, event, command, and canonical request digest. Reusing the same key with a different request body must return a conflict.

## 3. Authentication and authorization contract

### 3.1 Login flow

Use OIDC Authorization Code flow with PKCE where supported. The backend must:
1. Create a cryptographically random, single-use state and nonce.
2. Bind the authorization transaction to the initiating browser session.
3. Redirect to the configured issuer.
4. Validate callback state and exchange the authorization code server-side.
5. Validate the ID token signature, issuer, audience, expiry, nonce, and applicable authorized-party claims.
6. Resolve immutable issuer + subject against the active operator registry.
7. Establish a short-lived server session; do not expose refresh tokens to browser JavaScript.
8. Record login outcome and assurance metadata without storing bearer tokens in the audit journal.

PKCE/state/nonce randomness protects the authentication flow only. It is not used to choose a winner.

### 3.2 Server-derived actor context

Every privileged handler derives this context from the verified server session:

```json
{
  "actor_issuer": "https://issuer.example.invalid/",
  "actor_subject": "subject_synthetic_operator_A",
  "operator_ref": "operator_synthetic_A",
  "roles": ["DRAW_OPERATOR"],
  "auth_time": "2026-11-11T12:00:00Z",
  "assurance": "MFA_REQUIRED_AND_VERIFIED",
  "session_id_hash": "sha256:synthetic_digest"
}
```

All values above are illustrative. The client must never submit or override actor identity, roles, MFA assurance, session hash, or approval identity.

### 3.3 Role matrix

| Role | Allowed actions | Explicitly not allowed |
|---|---|---|
| DRAW_OPERATOR | Create/edit draft, request freeze, request execution after approvals | Approve own rules/snapshot; independently verify own result |
| DRAW_REVIEWER | Review and approve rules/snapshot; verify proof | Approve own prepared snapshot; rewrite roster |
| DRAW_PUBLISHER | Approve public result projection | Change draw result or roster |
| DRAW_AUDITOR | Read restricted evidence and independently reproduce proof | Mutate draw state |
| DRAW_SECURITY_ADMIN | Manage operator grants/revocations under dual control | Approve own role grant or own draw |
| SERVICE_IDENTITY | Perform narrowly scoped backend tasks | Interactive human approval |

A human may hold multiple roles only if policy permits, but role overlap never removes the distinct-subject requirement for a particular approval pair. The same issuer + subject cannot satisfy two-person control. Shared accounts are prohibited.

## 4. Endpoint catalogue

All names are logical. Every privileged command requires authentication, authorization, CSRF protection where applicable, idempotency, expected version, durable journal acknowledgement, and state-machine validation.

### 4.1 Session and operator endpoints

| Method / path | Access | Purpose |
|---|---|---|
| GET /api/v1/session | Authenticated | Return minimal current actor/session state |
| POST /api/v1/session/logout | Authenticated | Revoke current server session |
| GET /api/v1/operator/me | Privileged | Return current operator's own role/scope |
| GET /api/v1/operator/registry | DRAW_SECURITY_ADMIN + independent approval policy | Read operator registry metadata |
| POST /api/v1/operator/grant | DRAW_SECURITY_ADMIN + separate reviewer | Grant a role to an immutable issuer/subject |
| POST /api/v1/operator/revoke | DRAW_SECURITY_ADMIN + separate reviewer | Revoke role/session access |

Never expose raw provider tokens or secrets through these endpoints.

### 4.2 Event and rules endpoints

| Method / path | Access | Purpose |
|---|---|---|
| POST /api/v1/events | DRAW_OPERATOR | Create draft event |
| GET /api/v1/events/{event_id} | Authorized draw roles | Read event metadata and current state |
| PATCH /api/v1/events/{event_id} | DRAW_OPERATOR, DRAFT only | Edit draft using expected version |
| POST /api/v1/events/{event_id}/publish-rules | DRAW_OPERATOR | Submit rules for independent review |
| POST /api/v1/events/{event_id}/approve-rules | DRAW_REVIEWER, distinct subject | Approve exact rules hash and cutoff |

Rules become immutable after approval. Any change creates a new version and invalidates prior approvals.

### 4.3 Snapshot and freeze endpoints

| Method / path | Access | Purpose |
|---|---|---|
| POST /api/v1/events/{event_id}/freeze-request | DRAW_OPERATOR | Request eligibility snapshot |
| GET /api/v1/draws/{draw_id}/snapshot-summary | DRAW_REVIEWER / DRAW_AUDITOR | Read count, policy version, commitment, not roster |
| POST /api/v1/draws/{draw_id}/approve-snapshot | DRAW_REVIEWER, distinct from preparer | Approve exact snapshot commitment/count |
| POST /api/v1/draws/{draw_id}/commit-beacon | Service policy after approvals | Bind a future chain hash and round |

The private participant snapshot is never returned by a public or ordinary admin endpoint. Reviewer access to the underlying roster is a separate, explicitly authorized private evidence operation and must be logged.

### 4.4 Draw execution and verification endpoints

| Method / path | Access | Purpose |
|---|---|---|
| POST /api/v1/draws/{draw_id}/execute | DRAW_OPERATOR after all gates | Request one deterministic draw operation |
| GET /api/v1/draws/{draw_id}/status | Authorized draw roles | Read state and operation status |
| GET /api/v1/draws/{draw_id}/proof | DRAW_AUDITOR / authorized reviewer | Read restricted proof artifact |
| POST /api/v1/draws/{draw_id}/verify | DRAW_REVIEWER, not executor | Independently reproduce and verify result |
| POST /api/v1/draws/{draw_id}/reconcile | DRAW_AUDITOR + security policy | Resolve ambiguous partial operation with evidence |

The execute endpoint must not accept a winner, participant index, random value, beacon round, chain hash, or roster from the browser. Those values are derived from approved server-side records.

### 4.5 Publication endpoints

| Method / path | Access | Purpose |
|---|---|---|
| POST /api/v1/draws/{draw_id}/publication-request | DRAW_OPERATOR or DRAW_PUBLISHER | Prepare public projection |
| POST /api/v1/draws/{draw_id}/approve-publication | Independent DRAW_PUBLISHER / reviewer | Approve exact projection digest |
| POST /api/v1/draws/{draw_id}/publish | Service after approval | Publish strict public result projection |
| POST /api/v1/draws/{draw_id}/withdraw | DRAW_OPERATOR + independent reviewer | Withdraw under published policy, preserving history |

Public endpoints are read-only and expose only records in PUBLISHED state.

### 4.6 Public endpoints

| Method / path | Access | Purpose |
|---|---|---|
| GET /api/v1/public/winners | Public | Paginated published winner summaries |
| GET /api/v1/public/winners/{public_result_id} | Public | One allowlisted public result |
| GET /api/v1/public/events/{public_event_id}/proof-summary | Public | Safe proof metadata only |

No public endpoint accepts a participant ID, raw member ID, roster cursor, private draw ID, or arbitrary storage reference.

### 5.5 PublicWinnerProjection

The public API may return only:
- public_result_id;
- public event title;
- public prize description;
- generic verified-result message;
- optional server-generated masked Member ID, only if the uniqueness/re-identification gate passes;
- publication timestamp;
- protocol version and safe proof summary/digest;
- verification status and public withdrawal status, where applicable.

It must never return winner name, nickname, alias, full/raw Member ID, phone, email, Telegram identity, MT5 login, deposit/payment data, participant list, private winner reference, secret salt, raw roster, internal actor subject/email, or private storage reference. If masking fails or collides, omit the identifier and use generic copy.

## 6. State machine and allowed transitions

### 6.1 Draw lifecycle

| Current state | Command | Next state | Required gates |
|---|---|---|---|
| DRAFT | submit rules | RULES_REVIEW_PENDING | Complete rules, policy version |
| RULES_REVIEW_PENDING | approve rules | RULES_APPROVED | Independent reviewer, exact digest |
| RULES_APPROVED | request freeze | FREEZE_PENDING | Cutoff reached/defined, policy valid |
| FREEZE_PENDING | snapshot complete | SNAPSHOT_REVIEW_PENDING | Private snapshot committed |
| SNAPSHOT_REVIEW_PENDING | approve snapshot | SNAPSHOT_APPROVED | Reviewer distinct from preparer |
| SNAPSHOT_APPROVED | commit future beacon | BEACON_COMMITTED | Future round, chain pinned |
| BEACON_COMMITTED | execute | DRAW_PENDING | Operator authorized, approvals valid |
| DRAW_PENDING | draw operation complete | DRAWN_UNVERIFIED | Proof artifact durable |
| DRAWN_UNVERIFIED | independent verify | VERIFIED | Signature and index independently reproduced |
| VERIFIED | request publication | PUBLICATION_REVIEW_PENDING | Public projection digest created |
| PUBLICATION_REVIEW_PENDING | approve publication | PUBLICATION_APPROVED | Independent approver |
| PUBLICATION_APPROVED | publish | PUBLISHED | Journal and public write acknowledged |

Exceptional states:
- CANCELLED: only under prepublished rules and independently approved.
- VERIFICATION_FAILED: no winner publication; preserve all evidence.
- RECONCILIATION_REQUIRED: ambiguous write, timeout, conflicting read-back, or journal failure.
- WITHDRAWN: public projection withdrawn under policy; historical evidence remains.

No direct transition may skip a required state. No endpoint may set a state supplied by the browser.

### 6.2 Approval invalidation

Any change to rules, cutoff, eligibility policy, participant snapshot, participant count, snapshot commitment, protocol version, chain hash, beacon round, or public projection invalidates the approvals bound to the previous digest. Create a new version/attempt and preserve the old evidence.

## 7. Idempotency, concurrency, and error contract

### 7.1 Idempotency rules

- Every state-changing command requires an Idempotency-Key.
- Store a durable record keyed by a server-derived scope: event/draw + command + actor subject + key hash.
- Same key + same canonical request digest returns the original operation state/outcome.
- Same key + different request digest returns IDEMPOTENCY_CONFLICT.
- A pending operation is resumed/reconciled; it is never duplicated.
- Cache may accelerate lookup but cannot be the authority.
- A client-generated UUID may be used as a request key if generated with a secure API; it is not draw entropy and must never feed the winner-selection algorithm.

### 7.2 Error codes

| Code | HTTP | Meaning | Client behavior |
|---|---:|---|---|
| UNAUTHENTICATED | 401 | No valid session | Re-authenticate |
| FORBIDDEN | 403 | Role/scope insufficient | Stop; do not retry |
| STEP_UP_REQUIRED | 403 | Fresh MFA required | Complete provider step-up |
| SUBJECT_DISABLED | 403 | Operator revoked/disabled | Stop and notify security owner |
| SEPARATION_OF_DUTIES | 409 | Same person or invalid reviewer | Require independent authorized person |
| PRECONDITION_FAILED | 409 | Version/state mismatch | Refresh state |
| IDEMPOTENCY_CONFLICT | 409 | Same key, different request | Stop; investigate client bug |
| OPERATION_IN_PROGRESS | 202 | Existing operation pending | Poll same operation ID |
| RATE_LIMITED | 429 | Request throttled | Retry only after server guidance |
| BEACON_NOT_READY | 409 | Precommitted round not yet available | Wait; do not change round |
| BEACON_INVALID | 422 | Signature/chain/round invalid | Fail closed; security review |
| JOURNAL_UNAVAILABLE | 503 | Evidence store unavailable | No sensitive operation proceeds |
| RECONCILIATION_REQUIRED | 503 | Ambiguous partial result | Freeze further actions |
| VERIFICATION_FAILED | 422 | Independent reproduction failed | Do not publish |
| PUBLICATION_FAILED | 503 | Public projection write unconfirmed | Reconcile same operation |
| VALIDATION_ERROR | 400 | Invalid input | Correct request |

Do not reveal whether a supplied member reference exists. Use generic validation errors for private identifiers.

## 8. Journal write protocol

For each state-changing command:
1. Verify session, actor subject, role, account status, MFA freshness, and separation-of-duties.
2. Validate request schema, expected version, and legal state transition.
3. Acquire a bounded concurrency lock or equivalent conditional write.
4. Resolve idempotency in durable storage.
5. Append an intent record to the independent journal and verify read-back.
6. Perform the logical state change using an atomic/conditional write where supported.
7. Verify durable state and associated proof artifact.
8. Append completion/failure record linked to intent; verify read-back.
9. Return success only after all required durable acknowledgements are confirmed.

If the journal is unavailable, do not freeze, execute, verify, publish, or withdraw. If a partial write is ambiguous, mark RECONCILIATION_REQUIRED when possible and block subsequent commands until a reviewer reconciles evidence. Never create a second draw because a browser timed out.

## 9. Public feed contract

Public responses are projections, not direct serialization of private database records.

Example:

```json
{
  "ok": true,
  "data": {
    "items": [
      {
        "public_result_id": "public_result_synthetic_001",
        "event_title": "MPS Demo Event",
        "prize_public_description": "Hadiah simulasi",
        "public_message": "Hasil undian telah diverifikasi dan dipublikasikan.",
        "masked_member_id": null,
        "published_at_utc": "2026-11-11T12:30:00Z",
        "verification_status": "VERIFIED",
        "proof_summary": {
          "protocol_version": "MPS-DRAW-V1",
          "participant_count": 25,
          "proof_digest": "sha256:synthetic_digest"
        }
      }
    ],
    "next_cursor": null
  }
}
```

The sample is synthetic and must never be presented as an actual winner. Public proof summary does not prove roster completeness by itself. The public UI must avoid claims such as “fully publicly provable” unless a reviewed privacy-preserving proof establishes roster eligibility and completeness.

Public API protections:
- Strict field allowlist and output schema validation.
- No generic database-object serialization.
- No private query parameters or member identifiers.
- Rate limiting, cache-control policy, and safe error messages.
- Text rendered as text nodes; no arbitrary HTML.
- HTTPS-only links from reviewed destinations.
- Withdrawn results remain represented according to a documented public correction policy; private evidence is retained.

## 10. Contract test matrix

All tests use synthetic identities and synthetic participants. No production database is required.

| ID | Test | Expected result |
|---|---|---|
| AUTH-01 | Missing/expired token | 401; no state change |
| AUTH-02 | Invalid signature/issuer/audience/nonce | Reject; security event |
| AUTH-03 | Disabled subject or revoked role | 403; no state change |
| AUTH-04 | Client sends forged actor/role/MFA | Ignore/reject; server actor remains authoritative |
| DUAL-01 | Same subject prepares and approves | 409 SEPARATION_OF_DUTIES |
| DUAL-02 | Two sessions with same subject | 409 SEPARATION_OF_DUTIES |
| DUAL-03 | Approval targets stale digest | 409 PRECONDITION_FAILED |
| STATE-01 | Browser tries to set DRAWN/PUBLISHED directly | Reject |
| STATE-02 | Skip required state | Reject |
| IDEM-01 | Same key and same body retried | Same operation/result |
| IDEM-02 | Same key with different body | 409 IDEMPOTENCY_CONFLICT |
| IDEM-03 | Concurrent duplicate execute requests | Exactly one durable draw operation |
| JOURNAL-01 | Journal unavailable before execute | 503; no draw |
| JOURNAL-02 | Timeout after intent write | Existing operation reconciled; no second draw |
| JOURNAL-03 | Completion read-back mismatch | RECONCILIATION_REQUIRED |
| BEACON-01 | Wrong chain or round | Reject |
| BEACON-02 | Invalid signature | VERIFICATION_FAILED; no publication |
| BEACON-03 | Independent index differs | No publication; security incident |
| PRIV-01 | Public response contains name/alias/full ID | Test fails release |
| PRIV-02 | Mask suffix collision | masked_member_id omitted |
| PRIV-03 | Legacy name-bearing ticker row | Not eligible for public projection |
| PUB-01 | Unverified result requested for publication | Reject |
| PUB-02 | Public projection digest changes after approval | Approval invalidated |
| REC-01 | Browser reload/back during pending operation | Same operation state; no duplicate |
| REC-02 | Service restart during draw | Durable operation recovered/reconciled |

Release gate: all critical security/privacy/idempotency tests must pass in isolated integration tests, then independent code review and real browser/device checks must be completed. A local unit-test pass alone is insufficient.

## 11. Implementation sequence after approval

1. Confirm accountable owner, provider choice, operator/reviewer identities, and cloud cost/retention policy.
2. Select hosting and storage architecture; document data residency, access boundaries, backups, and recovery.
3. Build identity adapter alone and test token validation, account disablement, MFA freshness, and session revocation.
4. Build journal adapter and prove create-only/independent anchoring and recovery.
5. Build event/rules/approval state machine using synthetic data only.
6. Build snapshot freeze and private reviewer access.
7. Integrate a pinned drand verifier and deterministic protocol test vectors.
8. Build independent verification and publication gate.
9. Build strict public projection and privacy regression tests.
10. Perform threat-model review, integration tests, browser tests, Android tests, and disaster-recovery exercise.
11. Only after explicit separate approval consider any production integration.

No step in this sequence is authorized by this document.

## 12. Final implementation gates

**Not ready for implementation** until:
- provider and hosting owner are approved;
- at least two actual independent human reviewers/operators are assigned;
- token validation and MFA policy are proven in a sandbox;
- separate journal storage and retention governance are approved;
- draw protocol encoding and test vectors are frozen;
- the verifier can independently validate the beacon and result;
- private roster access and public privacy projections are tested;
- recovery behavior is demonstrated under injected failures.

**Current status:** official draw BLOCKED; roulette SIMULATION ONLY; public Winner Board must not claim an actual result without verified backend evidence.
