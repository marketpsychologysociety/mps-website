## DATA-01 audit findings and implementation order

Observed directly in `rebuild/v4.8.1/Code.gs`:

1. **Registration:** application and plan rows are appended under ScriptLock with compensating deletion. `audit_` itself is best-effort (it catches errors and returns `false`), but the original registration flow ignored that result and had no durable retry key. **DATA-01A now implemented in source:** a SHA-256 fingerprint of normalized registration fields creates a deterministic request-ledger key; a STARTED intent and stable Application Ref are persisted before business writes; identical retries return the original result; both rows are reconciled after an ambiguous acknowledgement; partial state is quarantined as NEEDS_RECONCILIATION. The ledger stores only the fingerprint, not raw registration fields.
2. **Active IB deposit:** private Drive proof, deposit row, Telegram link, and application status are written as one compensated sequence. The audit append occurs after that sequence; failure can return an error for a committed deposit. The admin Telegram backup is sent inline after audit, so it has no durable retry record. If Telegram accepts a message but the call result is lost, a blind resend can duplicate the backup.
3. **Regular QRIS payment:** similar Drive/Sheets/link sequence and inline Telegram backup. The compensation path restores app/plan/payment/link state for known exceptions, but does not provide a durable outbox or a general ambiguous Drive-create recovery key.
4. **Member renewal:** the renewal reference is generated before Drive upload and the code already attempts to rediscover the row after an ambiguous append. The Drive file is still a separate side effect and must be tied to an exact deterministic filename for safe orphan reconciliation.
5. **Admin approval:** snapshots and compensation cover the member row, application, deposit/payment, plan, ledger, and VIP queue. A partial/ambiguous multi-sheet outcome is not equivalent to an atomic transaction; failed compensation requires operator reconciliation and must never be auto-retried as a new approval.
6. **PIN issuance:** Script Properties salt/hash are updated and verified with rollback logic. Telegram delivery happens after property commit; a remote send success followed by lost acknowledgement is an ambiguous delivery, not proof the PIN was not sent. Reissuing a PIN invalidates the prior PIN, so retry must not silently generate another credential.

**Safe remediation sequence (no production migration):**

- DATA-01A: **registration only implemented in source** using the existing `MPS Request Ledger` sheet and a server-derived SHA-256 request key. Payment, renewal, and Admin approval still need their own operation intents and recovery rules. Do not trust a browser-provided key as authorization.
- DATA-01B: make business commit outcomes explicit. A committed operation must return its persisted result on retry; an unknown outcome must return a reconciliation-required response and must not create another file, payment, member ID, PIN, or Telegram effect.
- DATA-01C: persist Drive upload intent and deterministic file name before `createFile`; after ambiguous response, search only the configured private folder for that exact name, verify MIME/size/privacy, and reconcile. Never trash a file while its corresponding row outcome is unknown.
- DATA-01D: move Telegram admin backups and PIN delivery into a durable outbox with idempotent effect keys and `DELIVERY_UNKNOWN` handling. Do not blindly resend when Telegram may have accepted the message.
- DATA-01E: failure-inject every boundary, duplicate/concurrent retry, compensation failure, and restart/recovery. Keep operation journal retention bounded without deleting unresolved records.

Do not combine this work with a schema migration to production. The TEST storage schema may be extended only after the journal format and recovery invariants are covered by tests and a dedicated migration/preflight plan.

## Safe execution boundaries

- Synthetic CI and mocked Apps Script tests are not evidence of Google Apps Script runtime behavior.
- First shared runtime exercise must use a separately provisioned TEST spreadsheet, proof folder, backup folder, Telegram TEST bot, and Telegram TEST group.
- Before any destructive or state-changing TEST case, verify project marker, spreadsheet ID/name, folder IDs/names/privacy, bot username, and group identity. Stop if any check is ambiguous.
- Do not request or log plaintext passwords, PINs, TOTP seeds, bot tokens, webhook secrets, or member proof contents.
- No production deployment, production storage edits, production Telegram calls, or live member-data changes without explicit user authorization.
